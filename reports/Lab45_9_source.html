1. Introduction

This report covers what our group built between 31 August and 11 September 2026. The project is a batch data platform that turns Olist order data into clean, tested tables, then uses them to suggest related products and to find which products a seller needs to restock.

This was a foundation sprint, so we focused on four areas: bringing the data in, cleaning it, storing it in layers, and measuring what it contains. The warehouse models, API and dashboard are not built yet.

Our design documents disagreed about storage: some said MinIO, some the local filesystem. Rather than pick one, we wrote a storage interface with two versions behind it. 4. Data ingestion

Ingestion does three things only: check each file exists and has the expected columns, copy the bytes into the raw layer unchanged, and record what was copied. Cleaning happens later.

Before a table can be loaded it must have a contract listing its columns, key, date and numeric columns, and measured row count. A table without one cannot be loaded. This matters because if a source file changes, the pipeline stops instead of quietly producing different numbers.

We then write a manifest holding the row count, byte size and SHA-256 hash per table. Running ingestion twice on the same input gave identical manifests, showing the step is repeatable.

Three facts changed our code. First, order_items has no quantity column; each row is one unit, so quantity must be counted. Second, products has no name or description text, only character counts, so keyword search on names is impossible. Third, the translation file covers 71 of the 73 categories used, so the join must be a left join.

6. Data cleaning and validation

Each cleaning rule is a small function that takes a table and returns a table, and none read or write files. This means we can test a rule on five rows, and moving to Spark later would change only the reading and writing code. We read every column as text first, then convert types in one step.

RuleWhat it doesWhy we chose it
trim_whitespaceremoves spaces around values" 12.5 " must read as a number, not become empty
coerce_typesconverts dates and numbersone clear place where types are decided
derive_order_linesgroups unit rows and counts quantityOlist has no quantity column; 112,650 rows became 102,425 lines
build_order_productskeeps distinct order and product pairsa product must count once per order in the graph
normalise_categoryfills the empty category with unknown610 products had no category and would be unreachable
attach_english_categoryleft joins the translation filean inner join would silently drop two categories
flag_order_statusadds is_delivered instead of deleting rows2,963 orders are not delivered; deleting them hides the cancellation rate

Table 5. Cleaning rules and the reason for each.

The most important rule is derive_order_lines. Because each row of order_items is one unit, 10,225 rows repeat the same order and product. These are real multi-quantity purchases, not errors, so we added them together instead of deleting them. To prove we lost no sales in the process, the pipeline checks that total revenue is the same before and after the step. It reported R$ 13,591,643.70 preserved. If someone later replaces this step with a simple DISTINCT, the pipeline will fail instead of quietly losing 10,225 units of sales.

The result surprised us: Olist is cleaner than our design assumed. Every uniqueness and relationship check passed on the raw files, with no duplicate rows at all. Our cleaning is therefore about types, empty categories and grouping, not repairing broken records. The 775 orders without item rows are a real property of the dataset, so we warn and record why, so a future real problem is not hidden behind a known one.

This affects our restocking rule directly. Dividing a stock of 50 units by the median speed gives about 105 years of cover, so nothing would ever be marked urgent. The synthetic stock levels must therefore be generated from each pair's own sales speed, or the rule always returns the same answer.

9. Product graph findings

Our design fixed only two things: an edge means "same order", and the weight is the number of shared orders. We found five more choices that were never decided and tested each. Three of our assumptions were wrong.

ChoiceWhat we measuredOur decision
Node typeproduct level reaches 14.8% of the catalogue, category level 98.2%two levels, product first, category as fallback
Which orders countall orders give 4,058 pairs, delivered only give 4,022delivered only, matching the revenue figures
Weight meaningranking by shared orders and by Jaccard share nothing in the top 50keep shared orders, add lift as a second column
Minimum evidencesee Table 112 shared orders and both products sold 5 or more times
Tie breaking95.9% of products with 2 or more neighbours had equal weightsorder by shared orders, then lift, then product id
Directionconfidence differs by 2.84 times on average, up to 24.6 timesstore both directions as columns

Table 10. Graph parameters we tested and the decision taken.

The weight result surprised us most. We assumed dividing by how often each product sells would help. It does not: a product sold once and bought once with another product sold once scores the highest possible Jaccard value of 1.0, so normalising alone pushes noise to the top. It works only with a minimum evidence rule. Separating support from confidence comes from association rule mining [1], and precomputing item pairs instead of predicting them follows item-based collaborative filtering [2], [3] and the Amazon patents on item-to-item similarity [9], [10].

Minimum evidence rulePairs keptProducts servedShare of catalogue
no rule (our first design)4,0584,88514.83%
2 or more shared orders2073120.95%
2 shared orders, both sold 5+ times1472140.65%
3 shared orders, both sold 5+ times63940.29%

Table 11. Effect of the minimum evidence rule on coverage.

Every setting is uncomfortable. We chose the third row, which keeps only 0.65% of the catalogue at product level, and we report that rather than hide it. Our conclusion is that Olist cannot support product-level suggestions across the whole catalogue, so the category level must do most of the work. Graph neural networks [4] and session-based graph methods [5] target sparse data, but need denser input than we have and would break our explainability requirement.

We also added a way to check whether the graph works. We built it from orders before a chosen date, then counted how many later pairs it already held. With a 1 June 2018 split, 42 of 905 later pairs were present, a hit rate of 4.6%. Only 22.3% of test-period products existed in the training graph, so the limit is new products arriving, not our ranking method.

13. Limitations

  • The synthetic inventory file does not exist yet, so no restocking result appears in this report.
  • Cleaning is written in pandas, not Spark. The rules are shaped so moving to Spark would change only the reading and writing code. At 112,650 rows distributed processing is not required.
  • Product-level suggestions serve only 0.65% of the catalogue under our evidence rule, so the category level carries most of the work.
  • The hit rate of 4.6% is low, limited by new products arriving rather than by our ranking method.
  • Search cannot use product names because the dataset contains none.
  • Stock levels, reorder points and lead times will be created by us and are labelled synthetic throughout.

14. Conclusion and next steps

This sprint produced a working first half of the pipeline. Data is ingested against contracts with a manifest, stored in separate raw and processed layers on local disk or an object store, cleaned by small tested functions, checked by 18 quality gates, and described by measures and five figures. We also agreed coding standards and made a tool enforce them.

The most valuable output is not a chart. It is the measurement that only 3.28% of Olist orders hold more than one product, and only 14.8% of the catalogue is reachable by the product graph. That changes the design of the rest of the project, and we could not have known it without building the cleaning and analysis stages first.

Our next steps, in order, are to generate the synthetic inventory file from the observed sales speed, build the dbt staging, dimension and fact models with grain tests, load them into BigQuery, build the two-level graph with the ranking rules from Section 9, and serve the results through FastAPI.
